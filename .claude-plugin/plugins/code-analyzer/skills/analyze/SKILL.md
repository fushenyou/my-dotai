# Code Analyzer - 代码架构分析

帮助用户快速理解项目代码结构和框架设计思路，生成结构化的分析文档保存到 Obsidian 笔记库。

## 核心理念

不是简单罗列文件和目录，而是站在架构师视角解读项目：
- **为什么这样设计** — 设计决策背后的原因
- **模块之间如何协作** — 依赖关系和数据流
- **关键抽象和核心概念** — 框架的领域模型
- **从哪里开始阅读代码** — 建议的学习路径

## 分析流程

### 第一阶段：快速扫描

1. **识别项目类型** — 通过配置文件判断技术栈
   - `package.json` → Node.js/Web 前端
   - `pom.xml` / `build.gradle` → Java
   - `Cargo.toml` → Rust
   - `go.mod` → Go
   - `requirements.txt` / `pyproject.toml` → Python

2. **扫描目录结构** — 使用 Glob 和 Bash 命令快速了解布局
   - 顶层目录 → 理解模块划分
   - 配置文件 → 理解构建和依赖
   - 入口文件 → 理解启动流程

3. **读取关键文件** — 聚焦于揭示架构意图的文件
   - README / CLAUDE.md / CONTRIBUTING.md
   - 入口文件（main、index、app）
   - 路由定义 / 模块注册 / 依赖注入配置
   - 核心接口和类型定义

### 第二阶段：深度分析

根据项目类型和复杂度，选择重点分析维度：

| 分析维度 | 关注点 | 适用场景 |
|----------|--------|----------|
| 分层架构 | 表现层/业务层/数据层 | Web 应用、企业应用 |
| 模块通信 | 事件流、依赖注入、消息队列 | 微服务、插件系统 |
| 数据流 | 状态管理、数据绑定、响应式 | 前端框架、实时系统 |
| 核心抽象 | 领域模型、设计模式 | 复杂业务系统 |
| 构建体系 | 编译流程、打包策略 | 大型项目、开源项目 |

### 第三阶段：交互确认

在生成最终报告前，对以下关键决策使用 AskUserQuestion 与用户确认：

1. **分析范围** — 是否聚焦特定模块，还是全局概览
2. **分析深度** — 精简速览还是详细展开
3. **图表需求** — 用户希望生成哪些类型的图表

**交互话术原则**：
- 用简短的问题，一次不超过 2 个
- 提供具体的选项而非开放式问题
- 说明为什么需要确认（"我发现..."、"为了更准确地..."）

### 第四阶段：生成报告

将分析结果写入 Obsidian 笔记库，格式参考 [references/report-template.md](references/report-template.md)。

**保存规则**：
- **保存目录**：`/Users/fusy/workspace/ObsidianVault/NoteBooks/note/代码分析/`
- **主报告文件名**：`{项目名}-架构分析.md`
- **图表文件**：与主报告同目录
- **内容语言**：中文
- 保存前自动创建目录：`mkdir -p "/Users/fusy/workspace/ObsidianVault/NoteBooks/note/代码分析"`

## 图表生成策略

根据场景自动选择最合适的可视化工具。

### Excalidraw（复杂架构图）

| 图表类型 | 适用场景 |
|----------|----------|
| 系统架构图 | 整体系统布局、服务间关系 |
| 模块关系图 | 核心模块之间的依赖和通信 |
| 部署架构图 | 基础设施和部署关系 |

当需要生成上述类型的图表时，调用 `obsidian-visual-skills:excalidraw-diagram` 技能。

### Mermaid（结构化图表）

| 图表类型 | 适用场景 |
|----------|----------|
| 流程图 | 请求处理流程、数据流转路径 |
| 时序图 | 模块间交互、API 调用链路 |
| 类图 | 继承关系、接口实现 |
| 状态图 | 状态机、生命周期 |

当需要生成上述类型的图表时，调用 `obsidian-visual-skills:mermaid-visualizer` 技能。

### 图表生成规则

1. 图表内容使用**中文标注**
2. 每个图表有独立的文件，不嵌入 Markdown 报告中
3. 在报告中使用 Obsidian 链接引用图表：`![[图表文件名]]`
4. 图表文件名格式：`{项目名}.{图表类型}.md`

## 报告结构

```
# {项目名} 架构分析
> 一句话描述项目定位

## 速览卡片        ← 60秒理解核心信息
## 技术栈          ← 核心技术及其角色
## 架构全景        ← 架构图 + 设计决策
## 核心模块        ← 每个模块的职责和设计思路
## 数据流          ← 关键数据流转路径
## 设计模式与亮点  ← 值得学习的设计决策
## 推荐阅读路径    ← 从哪开始读代码
## 附录            ← 文件结构树、依赖关系
```

## 质量检查

生成报告前确认：
- [ ] 每个模块都有「为什么这样设计」的解释
- [ ] 架构图准确反映了实际代码结构
- [ ] 推荐阅读路径从易到难、从入口到细节
- [ ] 中文表达清晰，技术术语保留英文原文
- [ ] Obsidian 链接格式正确
- [ ] 图表文件已实际生成并保存

## 常见陷阱

- **只列出目录结构** — 这不是分析，用户可以自己 `ls`
- **过度泛化** — "采用了分层架构" 对理解帮助不大，要说明具体怎么分的
- **忽略设计意图** — 不仅要描述"是什么"，更要解释"为什么"
- **图表过于复杂** — 单个图表聚焦一个关注点
- **缺少学习引导** — 告诉用户从哪开始读代码
